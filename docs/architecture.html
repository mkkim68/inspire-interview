1요청 흐름

입구(채팅·폼·RFP) → 접수 → 에이전트 루프 → 계산·근거·RAG. 숫자는 초록색 계산 계층에서만 만들어지고, LLM은 ③ 문장 작성에만 연결됩니다.

화면API·검색접수 에이전트계산 (숫자의 유일한 출처) 견적 RAG (점선 = QUOTE_RAG=1 일 때만)LLM (③ 문장만) 실제가정가상

2에이전트 루프 — 상태 기반 분기

플래너는 "상태에 아직 없는 것"을 보고 다음 도구를 고릅니다. 일정 판단 결과에 따라 경로가 갈리고, QUOTE_RAG=1 이면 점선 두 단계가 추가됩니다.

유사 사례 중앙값과 공식 금액이 ±25% 밖이면 retrieve_cases 가 review.reasons 에 사유를 추가합니다 (숫자 자체는 바꾸지 않음). 테스트는 conftest.py 에서 QUOTE_RAG=0 으로 고정하고 RAG 테스트에서만 명시적으로 켭니다.

3RAG 3곳 — 검색 결과가 견적에 실제로 쓰이는 곳

검색은 "어떤 사례·조항·문단을 볼지"만 정합니다. 데이터는 모두 가상 data/quote/mock/.

① 유사 사례

무엇을 검색
가상 사례 30건 (1건 = 1청크, kind=mock_case), 과업 범위 문구로 하이브리드 검색 top-5
결과가 어디에
case_based_range: 사례 금액 × √(교수 수 비율) 가정 → 최소·중앙·최대 → cross_check 공식과 ±25% 비교, 벗어나면 검토 사유

6분석 포인트

숫자는 어디서 만들어지나

  • 금액·공수·할증·VAT는 quote.py 순수 함수에서만
  • 검색은 사례·조항·문단을 고르기만, LLM은 ③ 문장만 → 숫자를 만들지 않음
  • 사례 기반 범위도 정형 cases.jsonl 금액에서 코드가 계산
  • 문서(modules.md)와 코드 상수가 다르면 테스트 실패

LLM: 쓰는 곳 1 + 교체 지점 2

  • 사용: ③ draft_narrative — Claude(또는 Ollama)가 [n] 인용 문단 작성, check_citations 로 검증
  • 교체 지점: RulePlanner.next_action(state) → tool-use 플래너, intake.extract(text) → 구조화 추출
  • 모두 금액 계산과 분리 → 바꿔도 숫자는 그대로

데이터 경계: 실제 · 가정 · 가상

  • 실제 cases.csv 입찰공고 8건 (약식 0.27~0.9억 / 전사 4.5~8.9억), KOSA 2026 임금
  • 가정 단가표, 공수 계수, 할증률, 최대 8명, 서울대 기준 조건, √ 규모 보정
  • 가상 mock/ 사례 30건 · RFP 3건 · 제안서 문단 — RAG 동작 시연용
  • 교수 수 확인 사례 1건 → 계수 보정 불가 → 모든 견적 review.required

하이브리드 검색 — 이제 측정값이 있다

  • 유사 사례 검색 (e5, 질의 8개): MRR hybrid 0.65 > keyword 0.62 > vector 0.51 → 첫 순위 정확도는 하이브리드가 가장 좋음
  • Recall@5 는 셋 다 0.29~0.34 로 낮음 (정답: 범위 자카드 ≥ 0.5, 가상 데이터, 표본 작음)
  • RFP 조항(정확한 문구·숫자)과 ISP/ISMP 같은 약어에서 키워드 쪽이 보완
