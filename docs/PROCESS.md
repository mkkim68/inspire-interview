## 3. v1 — 가짜 데이터로 뼈대 세우기 (14:33~14:35)

**의도: 데이터가 없어도 "흐름"과 "검증 장치"를 먼저 완성한다.**

- 샘플 근거 문서 3개(`data/quote/`): 단가표(혼합 1,060만 원/MM), 과업 모듈 카탈로그, 서울대 사례 요약 — 모두 **"샘플 가정값"** 명시.
- 견적식: 모듈 기본 공수 × **연구자 수 규모 계수**(0.8/1.0/1.3) × 단가 + VAT.
- 에이전트: `RulePlanner` 가 `search_refs → estimate → render_quote` 를 고르고 trace 기록, 최대 반복 제한.
- 테스트를 먼저 쓰고(실패 확인) 구현. US2·US3 테스트는 US1 구현에 이미 기능이 들어가 처음부터 통과 → **일부러 버그를 넣어 테스트가 잡는지 확인**(문서 숫자 변경 → 1개 실패, 플래너 고장 → 5개 실패).
- 실제 서버(PgVector + e5)로 스모크 테스트 통과.

**이 단계에서 남긴 핵심 장치** (이후 설계가 바뀌어도 유지):
- 금액은 순수 함수만 계산 → 견적서 숫자 = 계산 결과임을 테스트로 고정.
- 근거 문서와 코드 상수가 다르면 실패하는 테스트.

## 4. 피드백 ① — 연구소장 예시: "조건이 다르면 금액도 달라야 한다" (14:40~14:55)

> 서울대가 교수 50명·3개월이었다면, 고려대 교수 100명·1개월은 금액이 달라야 한다.

**문제**: v1 은 기간 입력이 없고 규모를 구간 계수로만 반영 → 예시를 표현할 수 없음.

**설계 변경 (v2)**:
- 입력: 교수 수(필수) + 연구자 수(선택, 비우면 교수 × 5 가정·표시) + **기간** + 범위.
  - 교수 수와 연구자 수를 **둘 다** 쓰기로 결정(사용자 결정): 교수 수 → 기획·수주·성과 업무, 연구자 수 → 연구비 집행·시스템 규모.
- 공수 = Σ(고정 + 교수 × a + 연구자 × b).
- 일정 판단: 필요 인원 = 공수 ÷ 기간. 표준 4명보다 빠르면 **압축 할증**, 최대 8명 초과면 **실행 불가 → 대안 A(최소 가능 기간)/B(기간 유지·범위 축소)**.
- 플래너가 상황에 따라 분기(가능: price / 불가: propose_options).
- 결과: 서울대 11.0MM·1.28억 / 고려대 2개월 16.0MM·할증 ×1.15·2.15억 / 고려대 1개월 → 불가 + 대안 2개.

**AI 산출물에서 사람이 잡은 문제**: 실행 불가인데도 의미 없는 "할증 ×1.45"가 견적서에 표시됨 → 수정 + 재발 방지 테스트.

**테스트 교체 메모**: spec 이 바뀌어 v1 규모 계수용 견적 테스트는 v2 기대값으로 교체. 템플릿 기존 테스트 13개는 유지.

| 그룹 | 건수 | 금액(VAT 제외) | 예 |
|---|---|---|---|
| 약식·부분 범위 ISP | 3 | 0.27억 ~ 0.9억 | 동명대 약식 ISP 3개월, 가톨릭관동대 AI ISP |

**발견 (가짜 데이터 모델과의 차이)**
1. 우리가 가정한 서울대 기준(11MM, 1.28억)은 실제 전사 ISP보다 4~7배 작다 (범위 차이는 있음).

4. 교수 수까지 확인된 사례는 1건(창원대) → 계수 보정 불가 (최소 3건).

**결정 (사용자)**: 2건으로 억지로 계수를 맞추면 "근거 있어 보이는 근거 없는 숫자"가 다시 생긴다 → 계수는 그대로 두고 **근거 상태를 견적서에 드러낸다**.

**설계 변경 (v3)**

- 에이전트에 `check_evidence` 도구 추가 → 응답에 `evidence`, `review: {required, reasons}`.
- 서울대 비교는 **"설명용 비교, 검증 아님"**으로 명칭 변경.
- 화면: "실제 사례 근거" 표(출처 링크·확인 수준) + "⚠ 담당자 검토 필요" 배지.
- 결과: 고려대 2개월 견적(VAT 제외 1.95억)은 두 그룹 사이 → 검토 사유 3개(보정 확신도 낮음 / 연구행정 범위 사례 0건 / 어느 그룹에도 근거 없음).

**AI 산출물에서 잡은 문제**: 방송대 금액 978,890,000 ÷ 1.1 이 float 오차로 889,899,999원 → `Decimal` 로 수정 + 테스트.

**테스트 변경 메모**: trace 순서 테스트에 `check_evidence` 단계 추가(검사 강화). 기존 13개 + 견적 테스트 모두 유지, 총 49개 통과.

## 8. 하이브리드 검색의 역할 재검토 → n-gram 도입 보류 (15:30)

- 질문(사용자): "하이브리드 검색은 기술 선택 이유가 없지 않나? 벡터 검색의 한계 상황이 이 과제에서 생기나?"
- 답: **현재는 없다.** 검색 대상 3개 문서, 검색 결과가 금액에 영향 없음, 사례 데이터는 정형 → 필터·계산이 맞는 도구.
  하이브리드가 필요해지는 시점은 RFP 업로드(정확한 문구·숫자), 사례 수백 건 유사 검색(ISP/ISMP/BPR 약어), 공고번호 조회.
- 키워드 검색이 한국어 조사를 처리 못 하는 문제(Postgres 'simple')도 확인 → **n-gram(pg_trgm) 도입은 보류**:
  측정된 문제가 없고, store 인터페이스·DB 확장 변경 범위가 크며 시간이 부족. "측정 후 도입" 기준을 한계에 기록.

## 9. 폼 → 대화형 접수 창구 (15:35~15:47)

- 문제 인식(사용자): 정해진 폼에 숫자를 넣는 방식은 입찰 담당자마다 다른 조건·표현("두 달", "고려대", "주 1회 보고")을 받지 못한다.
- 설계: **입구만 대화형으로 바꾸고 계산·근거·검토 판단은 그대로 재사용.**
  - `app/intake.py`: 규칙 기반 `extract()`(대학 약칭, 교수·연구자 수, 개월/주/두 달, 범위 키워드, '최대' 오인 방지),
    세션별 조건 누적, 부족하면 되묻기, 다 모이면 `run_agent`.
  - 견적식에 없는 요청(보고·상주·예산 등)은 버리지 않고 **'반영 안 된 조건'**으로 보여주고 검토 필요 사유에 추가.
  - `POST /chat`, 화면 상단 채팅창(기존 폼은 "직접 입력"으로 접음).
  - LLM 키가 생기면 `extract()` 만 교체 — 금액은 계속 코드가 계산.
- 결과: "고려대인데 연구비 관리랑 로드맵만 두 달 안에… 주 1회 보고도" → 교수 수 되묻기 → "교수 100명, 연구원 500명" → 견적 + 검토 사유 4개.
- AI 산출물에서 잡은 문제: 되묻기 메시지에 내부 키(`university=…`)가 그대로 노출 → 사람이 읽는 요약으로 수정.
- 한계: 범위 정정("로드맵은 빼줘") 미지원(처음부터 다시), 규칙 추출이라 표현이 다양하면 놓침(되묻기로 보완), 세션은 메모리.
- 테스트: 추출 6개 + 다턴 대화·반영 안 된 조건·리셋·세션 분리 4개 → 총 59개 통과.

## 10. 예산 상한 (15:44~15:46)

- 대화에서 "예산 1.5억 이하 / 1억 5천 / 8천만원 / 9000만 원 / 120,000,000원"을 인식(VAT 포함 상한으로 해석).
- 견적이 예산을 넘으면 `quote.fit_budget()`(순수 함수)이 예산 안 대안을 계산: A 표준 기간으로 늘려 할증 없애기, B 기간 유지·들어가는 범위만(카탈로그 순, 최적해 아님).
- 예산 초과는 검토 필요 사유에 추가. "예산" 문장은 반영 안 된 조건에서 제외.

- 테스트 변경 메모: `test_extract_nothing` 기대값에 `budget: None` 키 추가(검사 강화). 총 64개 통과.

## 13. 채팅 해석을 LLM으로 — 계산은 그대로, 해석만 (브랜치 `rag-quote`)

- 문제 인식(사용자): 정규식은 "300분 정도", "석 달", "1.5억 안쪽", "로드맵은 빼줘" 같은 애매한 표현을 못 알아듣는다. **LLM은 입력 해석에만** 쓰고 견적 계산은 그대로.
- 설계(`app/understand.py`):
  - Claude 구조화 출력(`client.messages.parse(output_format=Pydantic)`)으로 의도(조건/정정/처음부터/질문)·값·범위 추가/삭제·반영 안 된 요청을 받는다.
  - **원문 근거 검증**: 숫자마다 LLM이 원문 구절을 복사하게 하고, 코드가 ① 구절이 메시지에 실제로 있는지 ② 구절의 숫자와 값이 맞는지(주→개월 올림, 예산은 기존 파서로 재확인) 검사. 어긋나면 버리고 되묻기.
  - 숫자 없는 해석("석 달" → 3개월)은 "이렇게 이해했어요"로 사용자에게 되보여 준다.
  - `EXTRACTOR=llm` 일 때만 켜짐(기본 regex). 키 없음·네트워크·스키마 오류면 정규식으로 폴백.
  - 정정("로드맵은 빼줘")을 지원 — 정규식 시절 한계 해소.
- 실제 Claude 실행 결과: "교수님이 한 300분 정도, 석 달 안에, 1.5억 안쪽, 매주 진행 보고" → 교수 300·3개월·예산 1.5억 + 해석 메모 3개 + 반영 안 된 조건 / "연구비 정산이랑 특허 기술이전" → funding·outcome / "로드맵은 빼주세요" → 정정 / "서울대 건은 범위가?" → 질문.

- 한계: 채팅 1회당 LLM 1회 호출(지연·비용), 구절 검증은 숫자 일관성만 보며 "석 달"처럼 숫자 없는 해석은 사용자 확인에 의존.

- 질문(사용자): 경로가 일정 판단에서 두 갈래로만 나뉘는데 에이전트가 필요했나?

## 15. 설계 재검토 ② — RFP·제안서 청킹 크기 10000의 의미와 문제

- 현재: RFP 조항·제안서 문단은 `##` 제목 단위로 자르고 `make_chunks(..., 10_000)[0]` — 10000은 신중히 고른 크기가 아니라 "조항 안은 자르지 말라"는 의도.
- 의도한 부분: 검색 단위 = 의미 단위(조항). 200자 기계 분할이면 기간·예산 조항이 섞이거나 조항이 쪼개져 숫자 추출·인용이 틀어진다. 목데이터 최대 조항 165자라 문제 없었음.
- 발견한 문제(실측):
  1. `[0]` 만 가져와 10000자 넘는 조항은 **뒷부분이 오류 없이 버려짐.**
  2. e5 최대 입력 **512토큰**(한국어 45자 ≈ 30토큰 → 약 700~800자 이상은 잘림) → 긴 조항은 벡터 검색이 앞부분만 보고 판단.
- 개선안: `##` 조항 단위 유지 → 약 500자 넘으면 조항 안에서 재귀 분할 → 조각마다 조항 제목 접두 → ID `#조항.조각` → 전부 저장.
- **적용(사용자 결정: 가장 간단하게)**: 템플릿 `make_chunks` 의 "청크마다 제목 붙이기"를 그대로 재사용. 조항 제목 `## …` 을 `# …` 로 넘겨 조각마다 제목이 붙고,
  `SECTION_MAX=500`, source 에 조항 번호를 넣어 ID 가 `문서#조항#조각`, `[0]` 제거로 전부 저장.
  테스트: 1,000자 넘는 조항 → 여러 조각·조각마다 제목·끝 문장 보존·ID 중복 없음 (총 82개).
  실제 DB에 남아 있던 옛 형식 청크(제안서·RFP 11개)는 삭제 후 자동 재적재로 확인.

## 16. RFP 통로 정리 — 채팅과 별개의 '서류 입력' 통로

- RFP = Request For Proposal = **제안요청서**: 대학이 입찰 때 공개하는 문서(사업 개요·기간·예산·과업 범위·기타 요구사항 조항).
- `POST /rfp` 는 채팅과 별개의 입력 통로다. 채팅은 담당자가 말로 조건을 알려주는 것, RFP는 대학 문서에서 조건을 찾아 읽는 것. 두 통로의 결과는 같은 대화 세션의 조건 칸에 들어가므로, RFP로 시작한 뒤 채팅으로 정정할 수 있다.
- RAG를 쓰는 이유: 문서가 길어 숫자가 여러 곳에 나오므로 필요한 조항을 먼저 검색해 그 조항에서만 조건을 뽑는다.
- 경위: RAG 활용안 2번("RFP 업로드 → 조건 채우기")으로 제안·승인되어 구현했으나, 새 입력 통로라는 점을 충분히 설명하지 않아 사용자가 나중에 혼란을 겪음. 설명 후 **사용자 결정: 그대로 유지**(실제 입찰은 RFP 수령에서 시작하므로 현업 흐름에 맞음).
- 남은 일: 실제 RFP 파일(HWP/PDF) 업로드 화면은 없음 — 지금은 가상 RFP 버튼과 API의 `text` 입력만.
