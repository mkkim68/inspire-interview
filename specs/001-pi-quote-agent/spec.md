# Feature Specification: 대학 연구행정 PI 견적 에이전트

**Feature Branch**: `quote-agent`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "서울대 연구행정시스템 PI 같은 용역을 다른 대학이 문의하면 견적서를 만들어 주는
에이전틱 웹서비스. 대학명, 연구자 수, 과업 범위를 입력하면 공수·단가·소계·VAT·합계·출처가 담긴
견적서를 받는다. 필수 입력이 빠지면 되묻는다. 도구 호출 기록을 남기고, LLM 키 없이도 동작한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 입력값으로 항목별 견적서 받기 (Priority: P1)

사내 영업 담당자(또는 대학 담당자)가 웹 화면에서 대학명, 연구자 수, 원하는 과업 범위를 고르고
제출하면, 과업 모듈별 공수(M/M)·단가·금액, 소계, 부가세 10%, 합계가 정리된 견적서를 화면에서 바로 받는다.

**Why this priority**: 서비스의 핵심 가치. 문의 대응 시간을 줄이고 견적의 일관성을 확보한다.

**Independent Test**: 고정 입력(예: "고려대학교 / 연구자 2,000명 / 연구비 관리 + 실행 로드맵")으로 요청해
항목·금액·합계가 사전에 계산한 기대값과 정확히 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 단가표와 과업 카탈로그가 준비된 상태, **When** 대학명·연구자 수·범위 2개를 입력해 제출하면,
   **Then** 선택한 범위에 해당하는 항목만 담긴 견적서와 소계·부가세(소계의 10%)·합계가 표시된다.
2. **Given** 같은 입력, **When** 두 번 제출하면, **Then** 두 견적의 금액이 완전히 같다(결정적 계산).
3. **Given** 범위를 하나 더 추가해 제출하면, **Then** 합계는 이전보다 커진다.
4. **Given** 연구자 수가 더 큰 대학, **When** 같은 범위로 제출하면, **Then** 규모 계수에 따라 공수와 합계가 커진다.

---

### User Story 2 - 근거 확인 (Priority: P2)

담당자는 견적서의 각 항목이 어떤 근거 문서(단가표, 과업 카탈로그, 서울대 PI 사례)에서 왔는지 확인하고,
에이전트가 어떤 단계(근거 검색 → 계산 → 견적서 작성)를 거쳤는지 기록을 본다.

**Why this priority**: 견적은 금전 문서이므로 근거 없이 쓸 수 없다. 내부 검토·고객 설명에 필요하다.

**Independent Test**: 견적 응답의 출처가 모두 실제 적재된 근거 문서를 가리키는지, 처리 기록의 단계 순서가
정해진 순서와 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 견적이 생성됨, **When** 출처 목록을 보면, **Then** 모든 출처는 실제 근거 문서 이름이다.
2. **Given** 견적이 생성됨, **When** 처리 기록을 보면, **Then** 근거 검색 → 계산 → 견적서 작성 순서가 남아 있다.
3. **Given** 견적서, **When** 하단을 보면, **Then** "단가·공수는 샘플 가정값"이라는 안내가 있다.

---

### User Story 3 - 정보가 부족하면 되묻기 (Priority: P3)

필수 입력(대학명, 연구자 수, 과업 범위) 중 하나라도 빠지면 서비스는 견적을 만들지 않고,
무엇이 빠졌는지 알려주는 질문 목록을 돌려준다.

**Why this priority**: 잘못된 견적이 나가는 것을 막는다. 에이전트가 스스로 판단해 되묻는 동작을 보여준다.

**Independent Test**: 범위를 비워서 제출하면 견적 없이 "어떤 과업 범위가 필요하신가요?" 같은 질문이 온다.

**Acceptance Scenarios**:

1. **Given** 범위가 비어 있음, **When** 제출하면, **Then** 상태가 "정보 필요"이고 범위를 묻는 질문이 있다.
2. **Given** 대학명과 연구자 수가 모두 빠짐, **When** 제출하면, **Then** 두 항목 각각에 대한 질문이 있다.

### Edge Cases

- 연구자 수가 0 이하이거나 숫자가 아니면 → 되묻기(정보 필요)로 처리한다.
- 카탈로그에 없는 범위가 들어오면 → 그 범위는 무시하지 않고 "지원하지 않는 범위"로 알려준다.
- 근거 검색 결과가 비어 있어도(문서 미적재) → 계산은 수행하되 출처가 없다는 경고를 표시한다.
- LLM 키가 없으면 → 기본 처리 순서로 끝까지 동작한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 대학명, 연구자 수, 과업 범위(복수 선택)를 입력받아야 한다.
- **FR-002**: 과업 범위는 연구기획, 과제수주, 연구비 관리, 성과 활용, 차세대 시스템 구축 방향·실행 로드맵
  다섯 가지 중에서 선택한다. 모든 견적에는 공통 과업(현황 분석·To-Be 설계·프로젝트 관리)이 포함된다.
- **FR-003**: 시스템은 범위별 기본 공수 × 규모 계수 × 직급 구성별 단가로 항목 금액을 계산해야 한다.
- **FR-004**: 시스템은 소계, 부가세(소계의 10%, 원 단위 버림), 합계를 계산해야 한다.
- **FR-005**: 같은 입력에는 항상 같은 금액을 내야 하며, 견적서에 표시되는 숫자는 계산 결과와 같아야 한다.
- **FR-006**: 견적의 각 항목에는 근거 문서 출처가 있어야 하며, 출처는 실제 근거 문서여야 한다.
- **FR-007**: 시스템은 처리 단계(근거 검색, 계산, 견적서 작성) 기록을 응답에 포함해야 한다.
- **FR-008**: 필수 입력이 누락·잘못되면 견적 대신 누락 항목별 질문 목록을 돌려줘야 한다.
- **FR-009**: 처리 단계 반복에는 상한이 있어 무한히 반복하지 않아야 한다.
- **FR-010**: 외부 언어모델 키가 없어도 모든 기능이 동작해야 한다.
- **FR-011**: 견적서에는 단가·공수가 샘플 가정값이라는 안내가 있어야 한다.
- **FR-012**: 웹 화면에서 입력 폼을 제출하고 견적서·출처·처리 기록을 볼 수 있어야 한다.

### Key Entities

- **견적 요청 (QuoteRequest)**: 대학명, 연구자 수, 선택한 과업 범위 목록.
- **과업 모듈 (Module)**: 범위 이름, 기본 공수(M/M), 근거 출처.
- **단가 (Rate)**: 직급(책임/선임/전임), M/M당 단가, 투입 비율.
- **견적 항목 (LineItem)**: 모듈, 공수, 금액, 출처.
- **견적서 (Quote)**: 항목 목록, 소계, 부가세, 합계, 견적서 본문, 출처 목록, 처리 기록, 상태(완료/정보 필요).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 담당자는 입력부터 견적서 확인까지 1분 안에 끝낼 수 있다.
- **SC-002**: 같은 입력으로 100번 요청해도 금액이 100% 같다.
- **SC-003**: 견적서의 모든 항목(100%)에 근거 출처가 표시된다.
- **SC-004**: 필수 입력이 빠진 요청은 100% 견적 없이 질문으로 응답한다.
- **SC-005**: 외부 언어모델 키 없이 모든 사용자 시나리오가 통과한다.

## Assumptions

- 단가·공수·규모 계수는 공개 정보가 없어 **샘플 가정값**을 쓴다(서울대 PI 기사에 금액·기간 비공개).
- 서울대 사례 문서는 공개 기사에서 확인된 범위(연구기획–과제수주–연구비 관리–성과 활용, 차세대 시스템
  구축 방향·실행 로드맵)만 담는다.
- 규모 계수 구간: 연구자 1,000명 미만 0.8, 1,000~2,999명 1.0, 3,000명 이상 1.3 (가정).
- 사용자 인증, 견적 저장·이력, PDF 내보내기, RFP 문서 업로드는 범위 밖이다.
- 기존 사내 문서 RAG 기능(/ingest, /search, /ask)은 그대로 유지한다.
